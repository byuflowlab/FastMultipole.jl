## CUDA M2M Design

Use parent-gather accumulation, not atomics:

- Device-radix metadata from `020a` should provide parent records with up to
  eight child node indices and each child-to-parent displacement vector.
- One CUDA block or cooperative group owns one parent node.
- The block gathers each child multipole, applies child-to-parent M2M, accumulates
  into local/shared/register temporaries, and writes the parent multipole column
  exactly once.
- This avoids atomic adds into parent multipole columns and avoids a large
  child-contribution temporary/reduction buffer.
- Zero internal parent multipole columns before the upward pass. Do not zero leaf
  columns after B2M.

Avoid CPU-shaped GPU scratch:

- Do not allocate persistent device `work_a`/`work_b` `FlatCoefficientBuffer`
  slabs for M2M stages.
- Do not port CPU `m2m_operator_batch!` stage-by-stage as separate global-memory
  source-alignment, z-block, Lamb-Helmholtz, and return-alignment kernels.
- Prefer per-parent/per-child registers and shared memory for intermediate
  coefficients. Persistent state should be limited to body buffers, expansion
  buffers, device radix metadata, operator invariant cache arrays, and final
  output buffers.

Mathematical reference and constraints:

- Match CPU `m2m_operator_batch!` semantics for `CompressedComplexBasis`.
- Support `Val(false)` and `Val(true)` Lamb-Helmholtz order behavior:
  `P_phi` for phi and `P_active = P_phi + 1` for chi when LH is true.
- `Float64` is default. `Float32` remains opt-in.
- `MaterializedYRotationM2M` is the first CUDA behavior target.
  `FactoredRotationM2M` may be accepted as an alias to the materialized behavior,
  matching current CPU M2M/L2L fallback behavior.

## Device-Radix Requirement From 020a

The CUDA lifecycle should not call host `sortperm` or rely on host-built
`RadixGrid.perm`/`cell_ranges` as production source-of-truth metadata.

The intended device construction pipeline is:

1. Compute bounds on device, or accept explicit reusable bounds from the caller.
2. Launch a kernel to compute quantized coordinates, Morton keys, and stable body
   ids from resident bodies.
3. Sort `(Morton key, body id)` on device.
4. Detect key changes on device to build occupied leaf keys and leaf ranges.
5. Build occupied ancestor nodes and parent/child relationships on device.
6. Keep keys, sorted ids, ranges, node centers, and parent-gather child lists
   resident for B2M/M2M/M2L/L2L/L2B.

Host orchestration may read back small scalar counts if necessary, but production
CUDA code should not host-build route arrays, leaf ranges, or ancestor child
lists.

- Filename: `MATRIX_OPERATOR_REFACTOR/022a-explore-gpu-precomputed-operator-strategy.md`
- Table position: after `022`, before `019`.
- Blocking: all `022` dependencies plus `022`.

Purpose of `022a`:

- Evaluate larger GPU performance strategies before final operator tuning:
  fixed child-offset sets, level/offset batching, fused kernels, and precomputed
  dense device operators.
- Decide whether M2M and/or M2L should replace stage-by-stage rotation/z/LH
  execution with precomputed per-offset dense operators or fused kernels.
- Record benchmark evidence and a concrete recommendation before `019`.

Ideas to evaluate in `022a`:

- M2M has only eight child phases per level. Precompute one M2M operator per
  child phase/level/order if benchmarks justify it.
- M2L has translation-invariant offset classes from item `021`; batch by
  `(level, offset)` and benchmark cuBLAS strided-batched GEMM versus fused custom
  kernels.
- Avoid rebuilding trigonometric terms, z blocks, and rotation intermediates per
  route when offsets repeat.
- Compare dense precomputed operators against fused recurrence/rotation kernels
  for small and moderate `P`.
