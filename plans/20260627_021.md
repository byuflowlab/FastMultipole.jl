constant-`P` radix front-door plan.

Current relevant production surface:

- `src/containers.jl` defines `RadixGrid`, `ConstantPStencilConfig`,
  `RadixTraversalStrategy`, `RigidImplicitStencil`, `SparseOffsetIntersection`,
  `BlockedOccupancyBitsets`, `LazyMaterializedBatches`, `RadixM2LBatch`, and
  `RadixInteractionList`.
- `src/tree_batched.jl` defines radix-grid geometry helpers, Morton key encode/
  decode, occupied-cell lookup, body ranges, integer offsets, and displacements.
- `src/interaction_list_batched.jl` currently contains constant-`P` bound helpers,
  an eager `accepted_radix_stencil`, and a recursive `_radix_constant_p_stencil`
  implementation that materializes many hierarchical M2L transition offsets.
- `test/radix_interaction_list_test.jl` currently tests the recursive
  constant-`P` radix stencil behavior.
- Legacy octree interaction-list code in `src/interaction_list.jl` is separate
  and must remain unchanged.

Problem to fix:

- The recursive constant-`P` front door still produces too many abstract offsets
  at low `P` / high `ell`; it is not the predictable production stencil desired
  for the radix path.
- The code currently conflates two independent axes:
  1. the mathematical separation rule, such as classical FMM parent-neighbor
     M2L or constant-`P` analytic MAC; and
  2. the enumeration/layout backend, such as target-major, sparse intersection,
     bitset/block, or lazy materialization.

New direction:

- Make the first supported radix separation policy the classical uniform-grid
  FMM parent-neighbor rule:

```text
direct at the fixed leaf level:
    Chebyshev distance between source and target leaf cells <= 1

M2L at a same level:
    source and target parent cells are Chebyshev neighbors
    AND source and target cells are not Chebyshev neighbors
```

- For a dense interior target leaf cell, this yields exactly:

```text
27 direct candidates
189 M2L candidates
```

because the source parent can be any of the `3^3 = 27` parent neighbors, each
parent has `2^3 = 8` children, and the 27 child-neighbor cells are direct rather
than M2L:

```text
27 * 8 - 27 = 189
```

This is the predictable offset family desired for the radix path. Empty cells and
domain boundaries still filter candidates through the existing radix occupied-cell
lookup.

## Objective

Refactor item 021 so radix interaction-list construction separates:

- `RadixSeparationPolicy`: decides which cell pairs are mathematically direct or
  M2L; and
- `RadixTraversalStrategy`: decides how to enumerate/layout the occupied legal
  pairs.

Implement `ParentNeighborM2L` as the only active radix separation policy for now.
Comment out the current recursive constant-`P` radix policy path and its tests.
Keep standalone constant-`P` bound helper functions only if they are useful as
reference utilities and do not participate in active radix traversal.

The goal is a clean abstraction that makes it easy to add future policies such as
`ConstantPAnalyticMAC` without changing traversal backends, while avoiding the
current high-cost materialized constant-`P` offset front door.

## Design

Add a policy axis in `src/containers.jl`:

```julia
abstract type RadixSeparationPolicy end

struct ParentNeighborM2L <: RadixSeparationPolicy end
```

Keep the existing traversal axis:

```julia
abstract type RadixTraversalStrategy end
```

Update the public radix visitor/build signatures to include both axes:

```julia
foreach_radix_m2l_pair(f, traversal::RadixTraversalStrategy,
    policy::RadixSeparationPolicy, grid::RadixGrid; farfield=true)

foreach_radix_direct_pair(f, traversal::RadixTraversalStrategy,
    policy::RadixSeparationPolicy, grid::RadixGrid;
    nearfield=true, self_induced=true)

build_radix_interaction_list(traversal::RadixTraversalStrategy,
    policy::RadixSeparationPolicy, grid::RadixGrid;
    farfield=true, nearfield=true, self_induced=true)
```

Optional compatibility overloads may default to `ParentNeighborM2L()` for current
callers that pass only `(traversal, grid, ...)`. Do not preserve old overloads
that require `ConstantPStencilConfig` for active traversal.

Suggested low-level policy helpers:

```julia
_chebyshev_norm(d::SVector{3,<:Integer})::Int
_radix_is_leaf_direct(::ParentNeighborM2L, leaf_offset)::Bool
_radix_is_m2l(::ParentNeighborM2L, child_offset, parent_offset)::Bool
```

For `ParentNeighborM2L`:

```julia
_radix_is_leaf_direct(policy, d_leaf) = maximum(abs, d_leaf) <= 1
_radix_is_m2l(policy, d_child, d_parent) =
    maximum(abs, d_parent) <= 1 && maximum(abs, d_child) > 1
```

Use integer cell-coordinate offsets:

```text
d = target_coord - source_coord
```

Do not use Morton key deltas for offset math.

### Parent-Neighbor Candidate Tables

Implement procedural fixed tables rather than dynamic offset materialization.

Precompute a target-child-phase table for M2L candidates:

```text
target_phase in (0|1)^3
source_parent_offset in {-1, 0, 1}^3
source_phase in (0|1)^3

source_child_coord =
    2 * (target_parent_coord - source_parent_offset) + source_phase

child_offset =
    target_child_coord - source_child_coord
```

Keep a candidate iff:

```text
maximum(abs, source_parent_offset) <= 1
maximum(abs, child_offset) > 1
```

There should be exactly 189 candidates for each target child phase before
boundary and occupancy filtering. The union of possible leaf offsets over all
target phases is not the primary invariant; the per-target candidate count is.

Direct candidates are the fixed 27 offsets:

```text
d_leaf in {-1, 0, 1}^3
```

### Traversal Behavior

For the first implementation, it is acceptable for all active
`RadixTraversalStrategy` types to delegate to one shared correct target-major
enumerator for `ParentNeighborM2L`. The abstraction must still preserve the
strategy dispatch point so future strategy-specific optimized implementations can
replace the shared path.

M2L target-major enumeration:

```text
for each occupied target leaf cell:
    target_coord = radix_cell_coord(grid, target_cell)
    target_phase = target_coord .& 1
    for each precomputed candidate for target_phase:
        source_coord = target_coord - candidate.child_offset
        if source_coord is in-bounds and occupied:
            source_cell = radix_cell_index(grid, source_coord)
            emit (child_offset, target_cell, source_cell)
```

Direct target-major enumeration:

```text
for each occupied target leaf cell:
    target_coord = radix_cell_coord(grid, target_cell)
    for each d in {-1,0,1}^3:
        source_coord = target_coord - d
        if source_coord is in-bounds and occupied:
            if d == 0:
                emit only when self_induced=true
            else:
                emit only when nearfield=true
```

Switch behavior:

- `farfield=false` suppresses M2L visits only.
- `nearfield=false` suppresses non-self direct visits only.
- `self_induced=false` suppresses self direct visits only.
- Disabling one route must not reroute it to another route.

Batching behavior:

- `build_radix_interaction_list` groups emitted M2L pairs by leaf offset in
  `RadixM2LBatch`.
- `direct_pairs` stores the emitted direct cell pairs as before.

## Acceptance Criteria

- Active radix traversal uses `ParentNeighborM2L` as a `RadixSeparationPolicy`.
- Traversal/layout strategy dispatch is separate from separation-policy dispatch.
- No active radix traversal calls `_radix_constant_p_stencil` or materializes a
  recursive constant-`P` transition-offset list.
- For an interior target, the parent-neighbor policy emits exactly 27 direct and
  189 M2L candidate source cells before occupancy/boundary filtering.
- All four active traversal strategies produce identical emitted cell-pair sets
  for `ParentNeighborM2L`.
- Switch behavior matches the route-suppression semantics above.
- Legacy octree interaction-list code remains unchanged.
- Implementation and verification notes are recorded in
  `MATRIX_OPERATOR_REFACTOR/021-impl-constant-p-stencil-and-interaction-list.md`.
- Approval remains unchecked for a separate review pass.
