## Newly identified lever: intermediate rigid radii

The task-025 construction and exact-once proof are not intrinsically limited to
`q = 3` and `q = 12`.  Direct enumeration for every integer `q = 3:12` shows
downward monotonicity (`minimum child norm² > q`) throughout.  The distinct shells
are `q = 3,4,5,6,8,9,10,11,12` (`q=7` has the same lattice set as `q=6`).

At the target's fully occupied `ell=5` grid, exact directed work counts are:

| q | near offsets | phase offsets | direct cell pairs | total hierarchical routes |
|---:|---:|---:|---:|---:|
| 3 | 27 | 189 | 830,584 | 6,039,504 |
| 4 | 33 | 231 | 1,014,904 | 7,367,184 |
| 5 | 57 | 399 | 1,729,144 | 12,277,584 |
| 6 | 81 | 567 | 2,421,064 | 16,820,208 |
| 8 | 93 | 651 | 2,766,664 | 19,075,248 |
| 9 | 123 | 861 | 3,614,440 | 24,456,912 |
| 10 | 147 | 1,029 | 4,304,872 | 28,925,424 |
| 11 | 171 | 1,197 | 4,973,728 | 33,063,216 |
| 12 | 179 | 1,253 | 5,189,728 | 34,343,088 |

This matters because reducing `q` reduces both dominant workloads, rather than
trading one for the other.  Using the measured q=12 stage times only as a linear
first estimate, q=9 would reduce nearfield + M2L from about 25.7 ms to 18.1 ms;
q=6 would reduce it to about 12.3 ms.  These are projections, not performance
claims.  The sampled-direct error frontier is unmeasured and is the gating result.

Generalizing the production policy from `(3, 12)` to these shells requires a small
source change plus expanded task-025 coverage/classifier verification.  That is an
optimization-cycle decision and will not be made in this attribution-only pass.

## Other levers to retain or demote

Prioritize after the attribution data:

- **Intermediate rigid-radius sweep.** This is first because it reduces both
  dominant kernels and q=4 is modeled only ~0.4 ms above target.  It requires
  generalizing the policy/classifier tests, then measuring every distinct shell's
  timing and sampled-direct error.  No shell is admissible until that gate passes.
- **Descending per-level radius schedule.** If a uniform shell passes accuracy,
  test a larger q on cheap coarse levels and a smaller q at the expensive leaf.
  Cross-level exact-once geometry is established, but the accuracy benefit and
  transition-table production design are unmeasured.
- **Tensor/mixed-precision leaf M2L.** At P=4 the dense operator is 16x16, exactly
  the shape where class-batched tensor-core work is plausible.  Test TF32/FP16 or
  BF16 operands with FP32 accumulation against the existing Float32 truncation
  gate.  The no-store A/B shows that arithmetic/input, not output traffic, is the
  residual mechanism.
- **Symmetric self-interaction specialization.** The near list is directed and
  inversion-symmetric.  For the single-system verdict workload, unordered cell
  and body pairs can in principle share one distance evaluation and update both
  endpoints.  This is close to a 2x work ceiling but needs a separate path because
  the general source/target API is not necessarily self-interaction.
- **Class- or target-owned M2L.** Current class-sorted routes reuse operators but
  atomically accumulate each route.  A class-persistent or target-owned mapping
  may trade repeated tile setup/atomics for fewer, longer-lived blocks.  The A/B
  bounds the atomic-only gain near 1.7 ms, so a rewrite must also improve input or
  arithmetic reuse to outrank the tensor experiment.
- **Counting sort for 15-bit Morton keys.** Still worth about the remaining
  2 ms grid stage, but it cannot close the target alone and follows the dominant
  work reductions.

Lower priority/high risk:

- native real-basis operators save only the unphysical m=0 imaginary lane
  (20% of coefficient lanes at code order 3), not a factor of two;
- target-cell-owned nearfield is demoted: although it can remove pair-list reads
  and improve source reuse, its expected atomic/store benefit was directly refuted
  by the 11.452/11.470/11.438 ms A/B;
- FFT/convolution M2L could exploit the full uniform leaf grid, but is a larger
  algorithm replacement and should follow the tensor/class-batching test;
- stale-tree/incremental refresh can save only the small rebuild remainder and
  still lacks a realistic-dt accuracy contract;
- expansion-order/radius co-design could trade higher P against smaller q, but
  the user-fixed task definition requires literature P=4 (`expansion_order=3`),
  so it is a specification change rather than an in-scope 028 lever;
- `ell` should be re-bracketed only after a radius or work-complexity change.

q=3:12 lattice shells, expand task-025 host/CUDA coverage, and run the full
