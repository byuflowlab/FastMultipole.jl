# Plan — Task 023e: Host `DenseTranslationM2L` resident M2L

## Summary

Implement and optimize the host-resident `DenseTranslationM2L` strategy as one
complete real coefficient-space operator per accepted full displacement class:

```text
L_target += S(delta_r) * M_source
```

Each `S(delta_r)` is a dense `D x D` matrix over the stacked degree-major
`[phi; chi]` layout. Application gathers every occupied offset class into
contiguous columns, performs chunked class GEMMs, and serially scatter-adds the
results so repeated targets accumulate correctly.

Completion has two mandatory gates:

1. Functional implementation and parity against the composed materialized-y
   oracle, concatenated resident M2L, and direct evaluation.
2. A measured optimization pass with reproducible functional-baseline and final
   results from non-macOS single- and multi-thread BLAS runs.

Local macOS results are smoke tests only. Cluster submission requires showing
the `sbatch` scripts and obtaining user permission.

## Confirmed implementation context

- The placeholder strategy is exported from `src/containers.jl`; its deferred
  throw is in `src/translate_batched.jl`.
- The recurring radix lifecycle emits routes in accepted-offset-class-major
  order. The functional baseline will nevertheless retain an explicit stable
  pack so packing can be measured and removed only if doing so wins.
- The dense row count is
  `D = degree_major_dof(P_phi) + (LH ? degree_major_dof(P_active) : 0)`, using
  `_dense_m2m_dof`, `_stacked_phi_rows`, and `_stacked_chi_rows`. Degree-major
  rows contain only physical degrees of freedom.
- Operator construction must use
  `m2l_operator_batch!(MaterializedYRotationM2L(), ...)` on identity columns.
  This is the already parity-tested reconstructed-`Ts(theta)` composition and
  is the sole convention oracle for dense construction.
- `DenseTranslationM2L` is host-only in 023e. CUDA support remains deferred to
  023f.

## Public API and plan types

### Strategy options

Replace the empty tag with:

```julia
DenseTranslationM2L(;
    max_persistent_bytes::Integer = 4 << 30,
    apply_chunk::Integer = 0,
    build_chunk::Integer = 0,
)
```

Semantics:

- `max_persistent_bytes > 0` limits the full persistent dense plan: operators,
  application slabs, and route metadata payloads.
- `apply_chunk >= 0`; zero means the largest per-class capacity. A positive
  value caps the number of gathered route columns per GEMM.
- `build_chunk >= 0`; zero means `D`. A positive value caps the number of
  identity columns sent through the construction oracle at once.
- `DenseTranslationM2L()` remains valid.
- Invalid or non-`Int`-representable values throw `ArgumentError` at strategy
  construction.
- The docstring states that the strategy is host-only, explains both chunk
  controls, and identifies 023f as the CUDA follow-up.

`CUDARadixLifecycleOptions` must enforce
`DenseTranslationM2L => MaterializedYRotationM2L`, mirroring the existing
precomputed-y pairing check. The dense apply path does not inspect or substitute
another operator convention.

### `ResidentM2LDensePlan`

Add a concrete host plan carrying:

```julia
route_class::Vector{Int32}
class_counts::Vector{Int}
class_starts::Vector{Int}
class_capacities::Vector{Int}
packed_sources::Vector{Int}
packed_targets::Vector{Int}
operators::Vector{Matrix{TF}}
src_slab::Matrix{TF}
dst_slab::Matrix{TF}
ndof::Int
width::Int
operator_bytes::Int
scratch_bytes::Int
route_metadata_bytes::Int
persistent_bytes::Int
construction_peak_bytes::Int
```

All arrays are allocated once at plan construction. Per-step refresh may mutate
only counts, prefixes, and valid packed prefixes. The footprint fields describe
array payload bytes exactly; `Base.summarysize` is a diagnostic cross-check and
is not required to equal payload accounting because it includes Julia object
headers and container overhead.

## Phase 1 — Functional implementation

### 1. Dense operator builder

Add a reusable internal builder workspace containing one invariant cache
reference plus construction buffers sized to `min(D, effective_build_chunk)`:

- flat source and target `FlatCoefficientBuffer`s;
- degree-major source and target buffers;
- `M2LOperatorScratch`;
- stacked input/output matrices; and
- prefilled uniform `phi`, `theta`, and `r` vectors.

Implement an internal in-place interface equivalent to:

```julia
build_dense_m2l_operator!(K, r, theta, phi, invariant, workspace, Val(LH))
```

For each identity-column block:

1. Zero the reusable source and target prefixes.
2. Place identity entries using the stacked phi rows and the M2M builder's chi
   convention: chi dof `i` occupies stacked column `D_phi + i`.
3. Convert to the flat oracle layout.
4. Apply `m2l_operator_batch!(MaterializedYRotationM2L(), ...)`.
5. Convert the result back to degree-major rows and copy it into the matching
   columns of `K`.

The plan constructor creates the invariant cache and builder workspace once and
reuses them for every displacement class. It must never call an allocating
convenience builder once per class.

Also provide the allocating test/debug convenience signature:

```julia
build_dense_m2l_operator(TF, basis_info, r, theta, phi, Val(LH))
```

This convenience method may allocate its own invariant cache and workspace.

### 2. Footprint estimation and limit enforcement

Implement a pure footprint helper that returns the five byte counts stored on
the plan. Use checked integer addition and multiplication for every dimension
and byte calculation. Convert overflow into an actionable `ArgumentError`.

The persistent estimate includes:

- all `D x D` operator payloads;
- both `D x apply_width` slabs;
- `route_class`, packed source/target arrays, class counts/capacities, and the
  `nclasses + 1` starts array.

The construction-peak estimate is reported separately and includes the
persistent payload plus the largest temporary builder payload that coexists
with it while the final operator is built. The configured limit gates persistent
storage; the error reports both persistent and estimated construction peak.

Compute class capacities and scalar byte totals before allocating operators or
slabs. Small metadata needed to determine capacities may be allocated first.
If `persistent_bytes > max_persistent_bytes`, throw before any large allocation.
The error must include:

- `D`, class count, apply width, and build width;
- operators, slabs, route metadata, persistent total, construction peak, and
  configured limit;
- remedies: raise the limit, lower `P`, disable Lamb-Helmholtz, or reduce
  `apply_chunk` when slabs are material. Do not claim that chunking reduces
  operator storage.

### 3. Free-function parity surface

Replace the existing `resident_m2l_batch!(::DenseTranslationM2L, ...)` throw
with a correctness-first implementation mirroring `DenseTranslationM2M`:

- accept nonuniform `(r, theta, phi)` by column;
- build and apply one dense operator per column;
- accumulate rather than overwrite targets; and
- preserve the physical `m=0` invariants.

This method is a parity surface, not the production grouped implementation.

### 4. Dense plan construction

Implement `ResidentM2LDensePlan(...)` next to the other M2L plan constructors.

For each accepted integer offset:

1. Compute `delta_r = TF(cell_width) * SVector{3,TF}(offset)` and obtain
   `(r, theta, phi)` with `cartesian_to_spherical`.
2. Compute the class capacity as
   `min(route_capacity, max_cells, product(max(G - abs(offset[k]), 0)))`.
3. Materialize exactly one `D x D` operator with the shared builder workspace.

Set `apply_width` to at least one and otherwise to the largest class capacity,
capped by a positive `apply_chunk`. Set the construction width to `D`, capped by
a positive `build_chunk`.

Offset-universe policy is explicit:

- Recurring `RadixFMMCache`: build every offset accepted by the configured
  stencil, including classes unoccupied in the current step because later
  refreshes may occupy them.
- One-shot immutable host state: build every distinct offset represented in
  `list.m2l_batches`; absent classes can never appear without rebuilding that
  state.

### 5. Production lifecycle wiring

- Extend `_radix_cache_workspace` to accept the dense strategy, validate the
  materialized-y pairing, and construct `ResidentM2LDensePlan` with the full
  accepted-offset vector and `G = 1 << ell`.
- Extend the one-shot `ResidentOperatorWorkspace` constructor. Skip legacy M2L
  groups, preserve the sorted interaction-list offset order, populate
  `route_class`, and perform the initial dense route refresh.
- Dispatch Dense before the generic materialized/shared fallthrough in
  `_launch_resident_m2l!`. The dense launcher validates both the operator pairing
  and concrete plan type.
- Add `_refresh_dense_m2l_routes!`: zero the histogram, count valid route
  classes, form starts, assert the histogram total, stable-pack sources and
  targets, and restore starts after using them as cursors. It must allocate zero
  bytes in steady state and preserve every array's identity.
- The dense launcher zeros locals at entry, matching the other complete M2L
  launchers. For each nonempty class and apply chunk, gather flat buffer rows
  into stacked degree-major order, call `mul!`, and scatter-add to flat locals.
  Gather/scatter use scalar `@inbounds` loops and the existing flat-index maps.
  Scatter must use serial `+=`; indexed `.+=` is forbidden because repeated
  targets would lose contributions.
- Use function barriers around plan-specific refresh and application loops so
  the loosely typed workspace field does not cause dynamic dispatch in kernels.

### 6. CUDA rejection

Dense must fail before CUDA workspace construction or upload in every entry
point. Make both `_assert_cuda_materialized_operator!` and
`_assert_cuda_supported_operator!` strategy-aware, or route both through a
single helper. The error states that Dense is host-only and CUDA is deferred to
023f.

Cover both:

- one-shot `cuda_radix_state`; and
- recurring `RadixFMMCache(...; device=true)`.

### Optimization candidates

Measure candidates independently and retain only reproducible wins that remain
parity- and lifecycle-clean:

1. Eliminate the stable pack and consume the already class-major recurring route
   ranges directly, retaining histogram/capacity assertions.
2. Iterate occupied classes in descending count if the ordering cost is paid at
   refresh rather than launch.
3. Measure dense GEMM versus a scalar kernel for narrow class widths.
4. Test operand orientation only if profiling identifies a layout bottleneck;
   `K * source_slab` remains the default.
5. Sweep `apply_chunk` for peak scratch versus GEMM efficiency.
6. Sweep `build_chunk`; consider per-class threaded construction only when build
   time is material and each thread owns independent oracle scratch.
7. Compare one- and multi-thread BLAS and record operational guidance without
   hard-coding a global BLAS thread setting.

## Assumptions and fixed decisions

- Dense construction and selection require `MaterializedYRotationM2L`.
- Matrices are stored as `Vector{Matrix{TF}}`, one contiguous matrix per offset.
- Matrices are built directly in `TF`; Float64-build-then-convert is considered
  only if measured Float32 accuracy requires it.
- The configured memory limit gates persistent dense-plan payloads; transient
  construction peak is separately estimated and reported.
- The functional baseline uses explicit stable packing. Removing it is a
  measured optimization, not an initial assumption.
- Locals are zeroed once at dense-launch entry, and every route contribution is
  accumulated exactly once.
