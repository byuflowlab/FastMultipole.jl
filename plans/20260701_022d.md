## Context: 2026-07-01 review findings (verified — do not re-derive)

The 022c increment is internally sound, but a fresh review with a realistic test
problem (400 random bodies in the unit cube, `RadixGrid(sys, 3)`,
`build_radix_interaction_list(LazyMaterializedBatches(1), ParentNeighborM2L(), grid)`,
`host_radix_state` + `run_host_radix_lifecycle!`) found **two blocking bugs** the
existing tests cannot see (the 5-body test grid is too sparse; end-to-end output parity
is only tested on a direct-only `ell=0` grid):

1. **Over-strong uniqueness assertion (crash).** `_assert_m2l_batch_targets_unique!`
   (`src/translate_batched.jl:1912`) requires unique targets per *whole* M2L batch, but
   `ParentNeighborM2L` batches (by ancestor offset, carrying leaf routes) legitimately
   repeat targets: on the 400-body grid, 316 of 632 batches have duplicates, so
   `_launch_resident_m2l!` throws `AssertionError` on any realistic input. The invariant
   that actually holds (verified: 0 violations on the same grid) — and the one the plain
   fancy-indexed add needs — is uniqueness **within each `(r,θ,φ)` subgroup** that the
   launcher already builds (`src/translate_batched.jl:1996-2005`): a target plus one
   concrete offset vector has at most one source.

2. **Far-field potential sign flip (silent wrong answer).** With bug 1 bypassed, the
   far-field potential equals **minus** the reference exactly (max abs diff vs `-ref`
   6.6e-6 at P=12, converging with P), while the gradient channel converges correctly
   (4.7e-4 / 1.9e-5 / 9.5e-7 at P=4/8/12). Root cause: the resident B2M kernels negate
   the strength (`q = -state.source_bodies[5, k]` in `_launch_host_b2m!`,
   `src/translate_batched_resident.jl:184`, mirrored in the two CUDA B2M kernels at
   `src/translate_batched_cuda.jl:896` and `:930`). Production convention
   (`test/gravitational.jl` `direct!`: `dϕ += q/(4πr)`, `d∇ϕ -= dx·q/(4πr³)`) is
   `φ = +q/(4πr)`, `∇φ = -q·dx/(4πr³)`. With `+q`, linearity gives the resident
   far-field `(+φ, -q·dx·invr³)` = production. The resident **direct-pair** kernels
   (`_add_host_direct_pairs!` `src/translate_batched_resident.jl:292`, and
   `_cuda_direct_pairs_output_kernel!` in `translate_batched_cuda.jl`) write gradient
   `+q·dx·invr³` — the *opposite* of production — so today near-field potential is
   right / gradient flipped, far-field potential flipped / gradient matching the flipped
   near-field. Fix both to the production convention (task 023 dispatches production
   `fmm!` into this lifecycle, so conventions must match).

Also noted (non-blocking, addressed in Phase 3):

- CPU `resident_m2l_batch!` is ~2-3x slower than the flat oracle with large per-call
  allocations (26 MB/call at P=12, N=512): `DegreeMajorMaps`, U/V mode blocks, and
  z-blocks are rebuilt inside every batch call instead of once per launch (the 022c
  plan specified per-launch; not done), and all stage temporaries are `similar`-allocated.
- `_launch_resident_m2l!` downloads `state.grid.node_centers` and per-batch route
  ranges via `Array(...)` every launch and builds `Dict` subgroups per batch — host
  metadata traffic on every GPU evaluation (does not violate the expansion-residency
  counter, but hurts the 008c break-even).
- CUDA L2B (`_launch_cuda_resident_l2b!`, `src/translate_batched_cuda.jl:1251-1294`) is
  still a `CUDA.@allowscalar` per-body host loop (known 022d scope; would also fail
  under `CUDA.allowscalar(false)` in the remote validation script).
