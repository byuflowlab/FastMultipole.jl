## Locked product and API decisions

- Extend `DenseTranslationM2L` with a configurable `cuda_headroom_bytes`
  keyword. Default: `1 << 30` (1 GiB). Require a nonnegative, Int-representable
  integer.
- Preserve the existing defaults and meanings of:
  `max_persistent_bytes=4 << 30`, `apply_chunk=0`, and `build_chunk=0`.
- Apply two separate CUDA construction gates:
  1. the dense-plan payload must not exceed `max_persistent_bytes`;
  2. the complete estimated device lifecycle footprint must not exceed
     `CUDA.free_memory() - cuda_headroom_bytes`.
- Report an actionable category breakdown on rejection: dense operators, route
  metadata, expansion buffers, packing/application slabs, other scratch,
  persistent total, estimated peak, configured cap, free memory, and reserved
  headroom. Recommend lowering P, disabling LH, reducing applicable scratch
  chunks, or selecting precomputed-y/factored/concat. State that chunking does
  not reduce dense operator storage.
- Never silently substitute another M2L strategy when the user explicitly asks
  for `DenseTranslationM2L`. Memory failure is explicit. Benchmark artifacts
  should record regimes where another strategy is preferable for task 024.
- Support dense CUDA through the recurring production cache only:
  `RadixFMMCache(...; device=true, options=CUDARadixLifecycleOptions(
  m2l_strategy=DenseTranslationM2L()))`. Keep the one-shot
  `cuda_radix_state` builders unsupported, but narrow their error to point users
  at the recurring cache, matching the 023b/023d pattern.
- Show the user every Slurm submission script and obtain explicit permission
  before submitting any job. Do not infer permission from this plan.

## Current implementation shape

### Public/internal types

`src/containers.jl` contains:

- `DenseTranslationM2L <: AbstractResidentM2LStrategy` near line 1065. It is
  documented as host-only and currently stores the three Int fields above.
- `ResidentM2LDensePlan{TF}` near line 1220. It is concretely host-typed:
  `Vector{Int32}`, `Vector{Int}`, `Vector{Matrix{TF}}`, and `Matrix{TF}` fields.
  This is why removing the CUDA guard alone cannot work.
- `CUDARadixLifecycleOptions` near line 1330. It already validates that dense
  M2L is paired with `MaterializedYRotationM2L()`.

Prefer a distinct internal CUDA plan type, defined beside the host plan in
`containers.jl`, rather than weakening all host fields to `Any`. Suggested
shape: `ResidentM2LDenseCUDAPlan` holding **only preallocated execution state** —
device Int32 `class_counts` histogram, pinned host count mirror, host
`class_starts` prefix, a packed device operator array, capacity-sized device
source/destination slabs, class capacities, D/width, byte accounting, and a
`whole_pass::Base.RefValue{Any}` execution bundle. Do **not** store a selected
apply policy or crossover threshold in the plan — those live in module-level
`const Ref` toggles (see step 4), matching `ResidentM2LFactoredPlan`
(`containers.jl:1135`) and `ResidentM2LPrecomputedYPlan` (`containers.jl:1170`),
which both keep counts/prefixes as the only mutable contents (verified by the
`CUDA.@allocated == 0` tests). The existing `ResidentOperatorWorkspace.m2l_concat`
field (declared `::Any` in `translate_batched.jl:2280`, not `containers.jl`) is
already flexible enough to carry different plan types.

`src/translate_batched_cuda.jl` is loaded behind the opt-in CUDA lifecycle.
Relevant points:

- `_assert_cuda_materialized_operator!` near line 1130 currently rejects dense

  recurring caches. Remove only this recurring rejection.
- `_assert_cuda_scratch_value!` recursively verifies operative plan storage is

  be `CUDA.AnyCuArray`.
- Factored route refresh (`_cuda_refresh_factored_m2l_routes!`, line 1530) and
  precomputed-y refresh (line 2008) both use device histograms plus pinned host
  count mirrors. Reuse this established pattern directly: call the shared
  `_cuda_class_histogram_kernel!` (line 1519) over the valid `route_class`
  prefix, do a single pinned `copyto!` of the counts to the host mirror, host
  prefix-sum into `class_starts`, and assert `class_starts[end] == n_routes`
  (class-major device emission guarantees contiguity). Build the reusable
  execution bundle once at construction into `plan.whole_pass[]`, following
  `_cuda_factored_whole_pass_setup!` (line 1831) and
  `_cuda_precomputed_y_whole_pass_setup!` (line 2041).
- `_launch_cuda_resident_m2l!` dispatches back through generic
  `_launch_resident_m2l!`, so add CUDA-specialized dense dispatch rather than a
  parallel lifecycle entry point.
- `_radix_cache_device_build` starts near line 2815. It currently allocates
  expansions, constructs `_radix_cache_workspace`, prepares compact CUDA plans,
  uploads accepted/rejected offsets, and increments `operator_uploads` once.
  Dense CUDA needs a pure preflight before large allocations and a device plan
  constructed/finalized only during this cache build.
- `update_cuda_radix_state!` refreshes device routes. Its primary method near
  line 3100 obtains
  `plan.route_class`, generates class-major routes, and explicitly refreshes the
  factored/precomputed plans. Add dense refresh here.
- Device route emission is already offset-class-major and contiguous. Therefore
  dense CUDA does not need the host plan's recurring source/target repack.
  Histogram counts plus prefix starts can address contiguous views of
  `state.route_sources` and `state.route_targets` directly.
- The lifecycle contract is: `route_uploads` and `operator_uploads` remain
  constant after construction, `expansion_host_copies == 0`, body uploads grow

  warmed M2L dispatch performs zero device allocation.

## Implementation sequence

### 1. Types, validation, and pure footprint preflight

- Add `cuda_headroom_bytes` to `DenseTranslationM2L`, its docstring, constructor
  conversion, and validation tests.
- Add a CUDA dense plan type beside `ResidentM2LDensePlan`.
- Factor/reuse overflow-safe accounting so a pure helper can estimate the dense
  CUDA plan and complete lifecycle before CUDA allocation. Include existing
  capacity formulas and all device state categories allocated by
  `_radix_cache_device_build`.
- Keep the existing host `max_persistent_bytes` behavior unchanged. The CUDA
  free-memory gate is additional and device-only.

### 2. Correct construction and construction-only upload

- Build every dense matrix from `build_dense_m2l_operator!` using the accepted
  offset and fixed cell width, exactly as 023e does.
- Functional baseline: construct a packed host `D x D x nclasses` array and
  upload it once during cache construction. Count this as the existing logical
  `operator_uploads` construction event; never increment it during refresh or
  evaluation.
- Prepare a packed device operator layout with each class matrix stored as a
  contiguous column-major slice. Allocate route histogram, slabs, and all
  scratch at capacity during construction.
- During profiling, compare bulk upload with pinned/streamed class staging (and
  device-side basis-column construction only if justified). Retain the faster
  approach while preserving the oracle-generated matrices and reported peak
  host/device memory.

### 3. Device refresh and functional reference path

- Implement dense route refresh as a device Int32 histogram over the valid
  `route_class` prefix, one pinned counts download, and a host prefix sum.
- Validate class IDs, histogram total, and class-capacity bounds. Empty route
  sets must produce all-zero locals without launches that assume nonzero work.
- Implement CUDA gather from `state.multipoles` into the stacked degree-major
  slab, one per-class `mul!`/cuBLAS GEMM over the valid width, and scatter-add
  into `state.locals`.
- Scatter must be collision-safe. Use atomic accumulation so concurrent or
  reordered class execution cannot lose contributions when multiple routes
  target the same local column.
- Keep this per-class gather/GEMM/scatter path independently selectable as the
  correctness/performance baseline.

### 4. Profile-driven optimization

This phase is prior-driven, not open exploration. 023b (factored), 023d
(precomputed-y), and 023e (dense host) already resolved most of the landscape:
per-class/grouped execution *as separate launches* is launch-bound and loses
20-500x at production occupancy; whole-pass execution wins at every occupancy;
and 023e already rejected apply-chunking as a speed lever, scalar-mult for narrow
classes, occupancy reordering, and operand transposition after finding no
launch/layout bottleneck. Lead with those conclusions.

**Lead design (build this first).** Dense's whole-pass analog is a *variable-group
batched/grouped GEMM*: each class's `D x D` operator applied to that class's
gathered columns, assembled once into the `plan.whole_pass[]` bundle at
construction. Unlike the factored/precomputed-y whole-pass (cheap per-column ops
over a flattened chunk with per-column indirection), dense cannot use that
chunked-flatten trick because every class carries a full dense operator. The
per-class `mul!` gather/GEMM/scatter path from step 3 is retained as the
independently-selectable reference baseline (`DENSE_CUDA_WHOLE_PASS[] = false`),
matching the 023e host `_launch_resident_m2l_dense_plan!`.

**Genuinely open — must be measured (dense-specific).** Because each dense class
does real O(D^2 * width) work, "launch-bound" is *not* a foregone conclusion here
(this is the key way dense differs from factored/precomputed-y). Measure on H200:

- batched-GEMM grouping strategy: cuBLAS batched vs grouped vs per-class, with
  occupancy-bucketed common D and bounded/padded widths;
- coalesced gather/scatter and atomic-scatter cost for repeated target columns;
- Float32/Float64 and LH-off/on memory crossovers — dense operator storage is
  `nclasses * D^2 * sizeof(TF)`, which is exactly why dense may not fit where
  factored/precomputed-y do (5-30x smaller footprint).

**Confirm-only — expect no change (do not re-explore).** Re-running these on CUDA
should reproduce the host 023e conclusions (`023e-...md:173-184`); confirm and
move on rather than sweeping: occupancy reordering, operand transposition,
apply-chunking as a speed lever, and scalar-mult for narrow classes. A route-wide
custom dense apply for tiny/partial classes is *contingent* on the batched-GEMM
measurement actually showing a launch-bound tail; do not build it speculatively.

Follow the established tuning-switch convention: module-level
`DENSE_CUDA_WHOLE_PASS = Ref(true)` and (only if chunking proves useful)
`DENSE_CUDA_CHUNK = Ref(1 << 14)`, mirroring `FACTORED_CUDA_WHOLE_PASS` /
`FACTORED_CUDA_CHUNK` (`translate_batched_cuda.jl:1743-1744`) and the
precomputed-y pair (`:1961-1962`). Do not store a per-plan crossover threshold —
023b/023d needed none, since whole-pass wins everywhere and the per-class path is
a test reference, not a runtime fallback. Only retain fused kernels when measured
data supports them.
