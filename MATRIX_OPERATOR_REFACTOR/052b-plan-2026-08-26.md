## 3. Implementation sequence

### Phase A — finish correctness and establish owned harness

#### A.1 Commit-ready shared-field and restart behavior

1. Audit the existing diffs above against current HEAD; preserve all unrelated
   changes and coordinate commits across files touched by another session.
2. Add an IGE multi-body save/restart test before removing the driver's
   remaining `ground_enable` restart guard. The reduced test must compare an
   uninterrupted run with a continuation across at least three post-restart
   steps and check per-rotor CT/force, ground strength/tangency, GS convergence,
   particle count, particle position/strength, and absence of duplicate loads
   or convection.
3. Test both checkpoint layouts:
   - New layout: several wakes reference one pfield and the particle cloud is
     written/loaded once under the first referencing wake.
   - Legacy layout: each wake has a distinct pfield and every particle cloud
     is written/loaded. This is the only compatible rescue route for the
     frozen private-field CPU jobs. Do not load those checkpoints into the new
     shared-pfield driver construction or silently concatenate/lose clouds.
4. Only after the IGE test passes, remove the driver ground-restart error.
   Deploy any live CPU-job rescue as a minimal warm-start/source patch on the
   frozen private-field tree; do not deploy the shared driver there.

#### A.2 Copy and own the GPU launcher

Create these FLOWPanel-owned files:

- `examples/run_rotor_multi_ground_effect_gpu.slurm.sh`, initially copied
  from the CPU multi-rotor launcher and thereafter owned by 052b.
- `scripts/p022g_submit_{1r,2r,4r}_{oge,ige}.sh`.
- `scripts/deploy_022g.sh`, targeting a separate cluster checkout such as
  `~/FLOWPanel-022g`; it must use checksum verification and must not overwrite
  the frozen CPU campaign tree.

The GPU launcher must:

- Keep one flat, unconditional carrier block and a six-case switch. Never let
  inherited defining knobs win.
- Apply the ruled settings in section 1, including 414 total steps.
- Wire the established 052 knobs (`VPM_ARRAYTYPE=cuarray`,
  `FLOWPANEL_GPU_INFLUENCE=cuda`, CUDA radix lifecycle, Julia 1.11.7,
  `FLOWPANEL_STEP_TIMERS=1`, `FLOWPANEL_GPU_TIMERS=1`). Use the 052c-selected
  device-resident particle FMM/SFS settings once its gates are green.
- Leave GPU-S disabled. Rotor `Backslash` factors and solves remain host-side
  until measurements prove that this ruling blocks acceptance.
- Fail loudly if CUDA/device-resident eligibility is missing. Permit a
  diagnostic fallback only through an explicit `GPU_ALLOW_FALLBACK=1`; an
  acceptance run may never set it.
- Never delete an existing result silently. Preserve/move it only when the
  caller explicitly requests that behavior.
- Print and record: git revisions for all three repos, GPU model, array type,
  GPU influence mode, radix settings, body/wake FMM settings, NROTORS,
  ground knobs, shared-pfield identity/capacity, requested/effective
  revolutions, spinup/acceptance/total step counts, solver construction time,
  and peak host/device memory.

Update the case metadata writer if those fields cannot be recorded entirely
by the launcher. Preserve monitor ordering/contracts.

### Phase B — measured multi-rotor gap audit

#### B.1 Instrument the actual interaction graph

The existing `influence_pass1/pass3` labels are too coarse. Emit separate,
env-gated timers for:

- particle self U/J and SFS;
- wake→rotor panels, wake→ground panels, and wake→probes;
- rotor panels→particles and ground panels→particles;
- rotor↔rotor and rotor↔ground cross influence inside each block-GS sweep;
- panel self/cached operator, each host `ldiv!`, GS iteration count;
- wake maintenance/propagation, monitors, VTK, and unclassified remainder.

Timer code must be allocation-free/default-off in ordinary runs and must not
double count nested categories. Verify that the sum reconciles with total
step time within timer resolution.

Actual routing anchors as of 2026-08-26:

- `_sa_wake_influence!` receives bodies plus wake probes as targets and wake
  systems as sources, so it includes wake→bodies/probes and particle self.
- `_sa_body_influence!` uses the same target set with bodies as sources, so it
  includes bodies→particles and body/body targets.
- `FLOWPanel_gpu_influence.jl::_gpu_device_pfield_target!` already routes the
  exact pfield self-pair through `UJ_fmm_gpu!`; non-self sources still use
  `direct_rectangular!`.
- The block-GS loop in `FLOWPanel_solver.jl::solve!(::Tuple,::Tuple)` performs
  cross-body `influence!` and one per-body solve for every body on every outer
  iteration. The ground uses `FlatGroundSolver`; only rotors own dense LU.

#### B.2 Reuse identical rotor operators on the host

Implement an opt-in shared-operator construction for `Backslash` so rotor 1's
assembled/factored G operator can serve translated/mirrored instances with
independent RHS, velocity, and potential work buffers. The previously measured
driver geometry gives max absolute G difference 9.3e-12 at the coarse mesh;
large relative differences occur only in entries about eight orders below
max|G|.

The API must validate element/DBC type, cell count/order, panel core size, and
the body-frame geometry/operator fingerprint. Shared solvers must reject
`update_G=true`, because mutating an aliased factorization would invalidate all
owners. Add solver unit tests for successful reuse, independent work buffers,
solution parity, incompatible-body rejection, and update rejection. The flat
ground remains unchanged.

This removes repeated ~160 s fine-mesh factorizations and roughly three of four
~10 GB rotor factors, but it does not remove the repeated host `ldiv!` cost.
Measure that cost separately.

#### B.3 Optimization decision ladder

First consume 052c's device-resident particle self-FMM/SFS result. Then run
the six-shape audit on one GPU model and optimize only measured blockers:

1. Keep current dense rectangular CUDA passes if the total projection clears
   the reserve gate below.
2. If rectangular work dominates, apply the already identified precision,
   far-field singular-switch, fast-math, and register-blocking hatches one at
   a time, each behind explicit knobs and CPU/GPU parity tests.
3. If still over budget, implement a source-tree traversal for many fixed
   targets, reusing stable tree topology and refreshing only geometry/strength
   data. Treat heterogeneous panel element types as separate source groups.
4. Implement the full two-grid rectangular radix FMM only if the source-tree
   route cannot clear the budget. The old rectangular-lift design note is a
   reference, not automatic Phase-B scope.

Keep the no-GPU-S ruling throughout this ladder. If host triangular solves or
GS orchestration alone prevent the target, stop and report the measured lower
bound plus the smallest GPU-S proposal for a new Ryan ruling; do not enable it
silently.

### Phase C — performance projection and gates

Do **not** extrapolate a one- or two-revolution time linearly. 052c measured
roughly N^1.5 growth in important wake work, so that method is invalid.

1. Use particle-count histories/checkpoints from the existing CPU multi-rotor
   arms at representative early, middle, and ten-revolution-equivalent states.
   When benchmarking the new shared field, combine all distinct rotor clouds
   from the same legacy checkpoint without changing positions or strengths.
2. Measure production-shape passes at several counts and fit each pass against
   its actual scaling variable (particles, panels, GS iterations), retaining a
   conservative upper confidence/envelope estimate.
3. Integrate the fitted per-step costs over the expected 414-step particle
   trajectory and add measured construction, compilation, monitor, and I/O
   costs. Record peak device/host memory.
4. A case is acceptance-ready only when projected elapsed time is at most
   **6480 s** (10% reserve below two hours), peak device memory leaves at least
   **20% headroom**, all major configured passes remain on their intended GPU
   path, and correctness gates pass.

Run a short production-shape wiring smoke for every case, but call it a wiring
smoke rather than a performance extrapolation. Keep all six comparable probes
on the same GPU model.

### Phase D — correctness and acceptance

Correctness has two deliberately separate references:

1. **Numerical CPU/GPU parity:** same commit, knobs, shared-pfield
   construction, and reduced geometry. Gate every changed pass and a short
   integrated 1r/2r/IGE simulation. This defines the arithmetic tolerance.
2. **Production physical comparison:** compare CT histories against the
   existing private-pfield `p022m` CPU arms. Derive and report a separate
   envelope from reduced shared-vs-private CPU smokes plus numerical parity.
   Do not describe this as exact arithmetic parity.

Submit each of the six acceptance cases independently after its projection
passes. A case passes only if:

- authoritative Slurm elapsed time, including setup and all 414 steps, is at
  most two hours;
- no CPU fallback, NaN/Inf, particle overflow, or device-memory emergency
  occurs;
- every block-GS step converges within the ruled tolerance/cap;
- CT stays within the declared physical-reference envelope, and per-rotor
  symmetry remains healthy;
- the timer ledger reconciles and records per-pass time/share and peak memory.

Report IGE/OGE CT ratio with per-revolution scatter for each rotor count. If a
case fails, report the measured dominant pass and lower bound; never relax the
two-hour, physics, or fallback rules silently.
