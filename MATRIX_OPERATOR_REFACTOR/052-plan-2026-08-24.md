## Gaps to close (the code work of this item)

All changes are opt-in / default-off per the 053 convention (no default-behavior change without user approval).

### G1 — S-matrix solve knob in the driver (FLOWPanel)
Without it, stage-c solve reverts to the ~7.3 s FMM path and the 3.3 s budget is unreachable.
- `examples/rotor_hover_pressure_comparison.jl:1027`: `RHPC_SOLVER_S` env (default `false`) → `pnl.Backslash(rotor; assemble_source_potential=true)`; print assembly wall time and S size.
- Guard the silent bypass: after the first solve (or at construction), print which branch `_source_influence!` takes — i.e. warn if `rotor.wake_correction_active[] == true` while S is assembled (S would be dead weight and the 0.607 s number wouldn't apply). One-time log, driver-level; no src default change.
- fm052_run.sh: `RHPC_SOLVER_S=1` in the GPU arm env for stages b and c (stage b doubles as the in-driver correctness test of the gemv path — the CPU reference arm keeps stock solve).
- BLAS, two-phase (user-ruled 2026-08-24): keep the existing startup setting (`:14`, from `BLAS_NUM_THREADS`, = job value 64) through solver construction so the one-time `lu!(G)` dgetrf (36,752², compute-bound O(N³)) gets all cores; then, right after solver construction and before time marching, `BLAS.set_num_threads(march)` with `march` from new env knob `BLAS_NUM_THREADS_MARCH` (**default: unset = no switch, current behavior** — 053 convention). Rationale: all per-step BLAS ops (S·σ dgemv + `ldiv!` triangular solves streaming the 10.8 GB LU factors) are bandwidth-bound; job 13395348 measured dgemv at BLAS 1/8/16/32/64 = 0.419/0.234/0.238/0.252/0.286 s ⇒ 8 is optimal, 64 is 22% slower. The step's BLAS section is serial (no Julia-threaded region runs concurrently), so no oversubscription concern either way. fm052_run.sh GPU arms set `BLAS_NUM_THREADS=64 BLAS_NUM_THREADS_MARCH=8`. NUMA-interleave + higher thread count (>46 GB/s single-domain ceiling) stays a named report lever, not done now.
