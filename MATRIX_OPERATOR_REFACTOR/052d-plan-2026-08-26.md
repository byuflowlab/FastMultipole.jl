## Objective

Replace the brute-force (dense) panel-influence legs of the 052 GPU step with
FMM-accelerated evaluation, cutting the two dominant flat panel legs:

| leg (timer label) | cost (probe 13497199, mature 209k) | scaling today |
|---|---|---|
| `rotor_panels_to_particles` | 1.98 s/step | O(N_panels · np) — linear in np with a large constant |
| `panel_cross_targets` | 0.82 s/step | O(N_panels²) cross-body — N-independent |
| (`wake_to_rotor_panels`, `wake_to_probes`) | 0.13 + 0.10 s/step | small; keep dense |

Context: total_step ≈ 6.0–6.3 s at np≈242k. The particle self-influence already
runs through the radix GPU FMM at 0.097 s/step — the panel legs are now the
largest single remaining cost (052c-plan-2026-08-26.md:303-312,642-645, P2
bullet 3 "flat panel legs — unruled").

## Where things stand (verified 2026-08-26 — do not re-derive)

1. **FLOWPanel already implements the full FastMultipole interface for panels.**
   `source_system_to_buffer!`/`get_position`/`get_n_bodies`/`direct!`/
   `buffer_to_target_system!`/`influence!` for `AbstractBody`:
   `FLOWPanel.jl/src/FLOWPanel_abstractbody.jl:1124-1357`; `body_to_multipole!`
   + `has_vector_potential` for lifting bodies
   `FLOWPanel_liftingbody.jl:706-1143`, non-lifting
   `FLOWPanel_nonliftingbody.jl:223-283`; `PanelWake` + `FilamentWrapper`
   `FLOWPanel_wake.jl:234-459,2818-2991`. `FastMultipoleBackend` calls
   `FastMultipole.fmm!`/`FmmPlan` (`FLOWPanel_fmm.jl:31-238`); the solver
   drives Krylov/FGS through it (`FLOWPanel_solver.jl:993-1021,1745-1792`).
   **So this item is routing, not new interface work.**
2. **FastMultipole's multipole formation supports every panel kernel FLOWPanel
   emits**: `Panel{Source}`, `Panel{Dipole}`, `Panel{SourceDipole}`,
   `Panel{Vortex}`, filament forms (`FastMultipole/src/bodytomultipole.jl:387,
   524-616,718-834`). FLOWPanel's dispatch maps ConstantSource/ConstantDoublet/
   VortexRing/mixed to these (`FLOWPanel_liftingbody.jl:736-950`,
   `FLOWPanel_nonliftingbody.jl:231-241`).
3. **The dense legs** pack true panels (17-row `RectangularPanelInfluence`,
   vertices + strengths + tag, tags 1–5) and particles (7-row
   `RectangularGaussianErfVortex`) and call `FastMultipole.direct_rectangular!`
   on device (`FLOWPanel_gpu_influence.jl:169-395`;
   `FastMultipole/src/direct_rectangular.jl:637-696,747,792`).
4. **The radix GPU FMM is strictly `targets === sources`** (particle
   self-influence only; `FLOWVPM_fmm_radix.jl:738,775`; v1 restriction
   050:34-39). "Rectangular" in the radix path means non-cubic bounds, not
   cross-system. Cross-system radix ("Option A",
   `theory/panel-multisystem-scoping.md:21-30`) was **REJECTED**: lifting
   `targets===sources` doesn't help because the radix path enforces one
   homogeneous source type (body_type/strength_dims/direct_kernel) —
   panel elements cannot coexist with point particles without a panel B2M
   + device direct kernel + heterogeneous strength plumbing inside radix
   (`:24-26,59`). Option B' (3-pass system-on-system + rectangular GPU
   kernels — the current architecture) was adopted instead; cross-system
   radix remains a stated long-term goal only (`:163-169`). Note the
   pricing that rejected Option A assumed panels→particles at "~0.4–2
   s/step"; it is now measured at the top of that range and grows
   linearly with np — which motivates THIS item, via a different vehicle.
5. **Routing seam already exists** (I3, APPROVED for P2 by Ryan 2026-08-26):
   `_sa_wake_influence!` has a split-call branch separating particle-field
   targets from small fixed targets (`FLOWPanel_simulate.jl:746-837`,
   split at `:782-796,810-825`), and `_gpu_rect_influence!` loops per target
   system (`FLOWPanel_gpu_influence.jl:619-660`). The panels→particles leg is
   dispatched at `FLOWPanel_gpu_influence.jl:654` (host-backed targets) and
   `:693-729` (`_gpu_device_pfield_target!`, device-resident targets).
6. **Problem sizes** (052 rotor-hover): rotor panels O(10³–10⁴) (mesh
   `40_40`…`45_185_ct4`), np grows to >242k at peak, 1080-step acceptance.
7. **Complementary, NOT this item**: panels-on-self AIC precompute
   (052c P2 bullet, `panel_self_cached_operator` 1.01 + `host_ldiv` 1.01
   s/step) — orthogonal to FMM routing; leave for its own ruling.

## Design

### Phase 1 (recommended v1): host tree-FMM for panels→particles

Route the `rotor_panels_to_particles` (and optionally
`ground_panels_to_particles`) leg through the EXISTING host `fmm!` path with
panel bodies as sources and the particle field as targets:

- **Mechanism**: in `_gpu_device_pfield_target!` / `_gpu_rect_influence!`,
  when the target is the particle field and the source is an `AbstractBody`,
  call `FastMultipole.fmm!((particle_targets,), (body,))` (via
  `FastMultipoleBackend`-style plumbing) instead of `direct_rectangular!`.
  Follow the I3 split-call pattern — small fixed targets stay dense.
- **Target view**: particles are device-resident in the 052 config. Reuse the
  existing host mirror (`_wake_monitor_host_pfield` /
  `_gpu_sync_mirror_from_device!`, `FLOWPanel_gpu_wake.jl`) for positions
  (D2H ≈ 6 MB at 242k, measured `d2h_mirror_sync` 0.054 s and it may already
  have run this step); accumulate U (+J) results back with one H2D copy +
  device axpy into the U/J rows (≈ 12·np·8 B ≈ 23 MB, a few ms on H200).
  A thin probe-like target system (positions in, U+J out; the existing
  `ProbeSystem` pattern) avoids touching FLOWVPM types.
- **Derivatives**: the leg needs U and J → `DerivativesSwitch` gradient +
  hessian on the target side (supported; dense leg's 12-row output today).
- **FMM parameters**: start from the solver pin (p=4, ncrit=50, theta=0.4,
  Barba MAC; `FLOWPanel_fmm.jl:111-119`) but treat (p, theta, leaf) for this
  leg as tunable; a `tune_fmm` pass or small sweep on the near-peak probe
  decides. Cache the `FmmPlan`/tree across the step's calls where possible;
  the panel tree (source side) is rebuilt per step only if the body moved
  (it rotates every step → rebuild; N_panels is small so the tree build is
  cheap).
- **Threads**: host fmm! is multithreaded; the H200 node allocation is 64
  CPUs, and the leg overlaps nothing today (fully synchronous) — expected
  cost O(0.2–0.5 s) vs 1.98 dense, bounded by a probe measurement (gate
  below). [Local dev runs: ≤4 threads.]

### Phase 1b (same mechanism): `panel_cross_targets`

The cross-body panel→panel leg (0.82 s/step) uses the same seam — targets are
another body's control points (a fixed small-to-moderate set). Route through
host `fmm!` only if N_panels² is actually large enough to win (at `40_40` it
may not be; at `45_185_ct4` it is). Decision by probe measurement, per mesh.

### Phase 2 (only if Phase 1's ceiling is insufficient): device-side panel FMM

The previously-scoped vehicle — cross-system radix (Option A) — is rejected
(see "Where things stand" #4): the blocker is source heterogeneity, not just
`targets===sources`. If Phase 1's host round-trip proves to be the bottleneck,
the realistic device options are, in increasing effort:

- **2a. Device L2B only**: form the panel multipole/local expansions on host
  (cheap: N_panels is small) and evaluate the local expansions + nearfield at
  the device-resident particles with a new device kernel — no host mirror of
  the targets, no radix surgery.
- **2b. Panels as first-class radix sources**: panel B2M + device panel
  direct kernel + heterogeneous strength plumbing inside radix
  (`theory/panel-multisystem-scoping.md:24-26` prices this as "strictly more
  work than (A)'s already-large aliasing surgery") — the long-term goal of
  `:163-169`, not something to start from this item.

Do NOT start either until Phase 1 numbers exist.

## Key risk: science fingerprint / gate tolerances

Dense panels→particles is exact; FMM is approximate. The 052 pinned CPU
reference and locked tolerances (CT cycle-mean diff ~5e-6 abs / 7e-5 rel,
Γ rms 5.4e-5) were generated with the dense leg. Switching introduces a
controlled error into every particle's convection. Options, for Ryan to rule:

- **(a) Hold the locked tolerances** — pick (p, theta) so the leg's field
  error ≪ gate tolerances (e.g. rel err ≤ 1e-6 → p likely 8–10; costs more
  than p=4), validate with the 36-step mature gate before any long run.
- **(b) Re-pin** — accept a modest (p=4-ish, ~1e-4) error, regenerate the
  pinned reference + tolerances once (the I6 machinery exists). More
  performance, new fingerprint.
- Recommendation: (a) first — it needs no re-pin and the panel-source
  expansion converges fast (smooth far field, small panels); fall back to
  (b) only if the probe shows the high-p cost erases the win.

## Implementation steps (after approval)

1. **FLOWPanel**: thin `ParticleTargetView` (positions + U/J accumulate,
   ProbeSystem-pattern, FastMultipole target interface) over the host mirror;
   route in `_gpu_device_pfield_target!` behind an env flag
   `PANEL_INFLUENCE_FMM` (default off → zero-risk deploy), with
   `_step_timer_measure(:rotor_panels_to_particles_fmm)` instrumentation.
2. **Parity testset** (local, host): panels→particles FMM vs
   `direct_rectangular!` on a shrunken rotor case — U and J rel-err vs p
   ∈ {4, 6, 8, 10}; asserts monotone convergence + threshold at the chosen p.
   Lives in FLOWPanel's suite next to the existing gpu-influence tests.
3. **Probe job** (H200, eng/qos=eng, ≤40 min, near-peak restart from the
   step-472 checkpoint): 5–10 steps, flag on, timer comparison
   (`rotor_panels_to_particles` dense vs fmm) + field-error snapshot at
   two p values. Gate: fmm leg < 0.6 s/step AND error compatible with the
   chosen tolerance option; otherwise stop and reassess.
4. **36-step mature gate** (`fp052c_mature_gate_run.sh` pattern, flag on):
   locked gates must pass under option (a). Only then consider flipping the
   flag on for long runs / acceptance-class jobs.
5. **Phase 1b decision** from the same probe's `panel_cross_targets` numbers.
6. Update this doc with results at each step; Phase 2 go/no-go ruling last.
