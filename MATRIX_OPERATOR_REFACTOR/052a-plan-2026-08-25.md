## Phase C decision gate — verdict APPROVED by Ryan 2026-08-25 (gate CLOSED; canonical copy now in `052a-impl-gh200-arm-unified-memory.md` Phase C)

**Verdict: NO unified/managed-memory adoption. Keep the discrete path as the
multi-arch default.** The adoption bar ("demonstrated capacity or bandwidth
win") is not met; if approved, this negative result moves to the 052a doc
per the Phase C spec.

Data: membench job 13477889 (GH200 C2C), CSV
`.../gh200/membench/job-13477889/fm052a_gh200_membench_13477889.csv`, and
the identical benchmark on an x86 H200 PCIe node, job 13478001
(`orc:~/FLOWPanel-052-h200/data/fm052_multiarch/h200/membench/job-13478001/`,
partition eng, wrapper `fm052a_h200_membench.sh` reusing the gh200 .jl
unchanged).

Provenance note: the plan's assumed "H200 PCIe numbers from the existing
H200 reports" never existed — `fm052b_gpu_s.log` (H200) crashed at
`FLOWPanel_solver.jl:450` on the `CUDA.MemoryInfo` API break BEFORE the S
upload ever ran, `fm052b_gpu.log` never enters the GPU-S path, and no
membench existed for any arch but gh200. The H200 column below is a direct
measurement from the twin membench run 2026-08-25 (Ryan-approved).

| Quantity | GH200 C2C (job 13477889) | H200 PCIe (job 13478001) | C2C / PCIe |
|---|---|---|---|
| H2D, ≥1 GiB, pinned | 374–380 GB/s | 55.4 GB/s | 6.8× |
| H2D, ≥1 GiB, pageable | 377–381 GB/s | 9.8–10.0 GB/s | ~38× |
| D2H, ≥1 GiB, pinned | 294–296 GB/s | 42.2–42.9 GB/s | 6.9× |
| D2H, ≥1 GiB, pageable | 296 GB/s | 16.1–16.2 GB/s | ~18× |
| H2D 1 MiB pageable/pinned | 95 / 171 GB/s | 14.3 / 42.5 GB/s | — |
| Pinning benefit at ≥1 GiB | none (≤1%) | 5.6× H2D, 2.6× D2H — required | — |
| One-shot S upload (10.805 GB, pinned) | 0.0287 s (~377 GB/s); repeat 0.0284 s | 0.1958 s (~55 GB/s); repeat 0.1958 s | 6.8× |
| Free HBM with S resident | 84.363 GiB of 95.577 GiB | 129.173 GiB of 139.801 GiB | — |

Gate reasoning (each adoption argument, against the numbers):

1. **Bandwidth win — none available.** Discrete staging on C2C already runs
   at ~memcpy speed (377–381 GB/s H2D; pinned ≈ pageable, so even the
   `_pin_host_array` best-effort path buys nothing here). Managed/unified
   memory migrates pages over the same C2C link; it cannot exceed it.
2. **Staging cost is already negligible.** The one-shot S upload is 0.029 s
   — vs the ~0.3 s/step rk3 target, and it happens once per run. Per-step
   body-buffer/influence-prefix traffic is MBs, i.e. tens of µs at these
   rates. There is no cost left for unified memory to remove.
3. **Capacity win — not needed at this problem size, and oversubscription
   would be a loss, not a win.** With S (10.06 GiB) resident, 84.36 GiB of
   HBM remains free — non-S overhead is only ~1.2 GiB. Holding the locked
   32 GiB post-upload reserve + 4 GiB margin, HBM alone supports S up to
   ~58 GiB (5.8× the current S; S ∝ N², so ~2.4× the panel count) before
   residency is blocked. Managed oversubscription into the 480 GB LPDDR5X
   would push past that, but spilled S pages would then serve gemv at C2C
   speed (~0.38 TB/s) instead of HBM3 speed (~4 TB/s) — a ~10× gemv
   slowdown — and per 052a any adopted change may touch only
   construction-time factories, never the graph-captured working set
   (CUDA error 900, job 13060540).

The measured comparison also sharpens the negative result usefully: the
GH200's discrete-path staging advantage over H200 PCIe is ~6.8× pinned
(~38× pageable), i.e. C2C already delivers, through plain `copyto!`, most
of what unified memory is usually adopted to get. Follow-ups: none
required to close the gate.
