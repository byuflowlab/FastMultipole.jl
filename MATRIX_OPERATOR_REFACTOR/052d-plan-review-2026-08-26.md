# Revised 052d — Shared-Grid, Role-Specific Panel Influence

> **See also:** `052d-plan-review-response-2026-08-26.md` (2026-08-26) — a
> response reviewing this document; its findings A–G amend the caching model
> (per-step rebuild under rotating panels), solver formulation
> (Backslash-per-rotor; coupled Krylov removed), staging, and gates.

## Summary

Do not approve the current 052d plan unchanged. Make the primary implementation
a device-resident cross-system FMM built around a **shared world grid with
role-specific trees**, not one heterogeneous particle+panel tree.

The selected architecture is:

- retain the existing particle radix tree for particle self-influence;
- retain the persistent per-body panel source/target trees used by each panel
  solver;
- add one combined world-aligned source tree containing the panels from all
  rigid bodies for post-solve panel influence and global panel-operator
  applications; and
- add one combined world-aligned target tree containing all panel control
  points, while reusing the particle tree as the particle target hierarchy.

The particle, combined-panel-source, and combined-panel-target trees should
share the world-grid definition, Morton convention, level geometry, and device
M2L operator tables. They should not share their Morton sorts, occupied-node
topology, coefficient arrays, output arrays, or leaf stopping rules.

This intentionally duplicates the relatively small panel geometry. The
duplication preserves the panel solver's stable leaf bookkeeping while the
combined tree aggregates distant bodies and avoids one panels→particles
traversal and launch sequence per rigid body.

Key corrections:

- Production 052 body→particle influence is **U-only**, because
  `BODY_HESSIAN_TO_PARTICLES=false`; particle self-influence still requires
  U+J/SFS (`FLOWPanel.jl/examples/rotor_hover_pressure_comparison.jl:441`).
- Keep cross-system positions, expansions, nearfield, and output accumulation
  device-resident; never use the full `ParticleField` host mirror.
- Start from the production body setting `p=8`, not the wake-FMM `p=4`
  setting.
- Treat topology reuse, multipole reuse, and target-output reuse as separate
  questions. Panel strengths change during the solve even when geometry does
  not, so a reusable tree does not imply reusable multipoles.
- Extend the existing GPU implicit offset stencil to distinct source/target
  occupancy maps; do not make a generic pairwise dual-tree traversal the
  production cross-system interaction builder.
- Host cross-system FMM remains an independent correctness/performance
  reference, not the production path.

## Why Not One Global Particle+Panel Tree?

Saving particle and panel indices is useful for scattering results and
preserving body identity, but it is insufficient for filtered FMM passes. A
spatial node containing both source classes has a multipole containing both
classes. A particle-only or panel-only pass would require all of the following:

- separate per-class multipole channels at every mixed node;
- per-node source-class occupancy masks;
- typed or indirect leaf ranges because a Morton leaf may interleave source
  classes;
- separate nearfield kernels and strength layouts; and
- separate validity tracking as particle and panel strengths change at
  different points in the step.

That is a heterogeneous-source FMM refactor, not index-based tree reuse. It
also conflicts with the current `RadixFMMCache` contract, which requires one
shared `body_type`, `strength_dims`, and `direct_kernel` and currently enforces
`targets === sources`.

A single global target tree is less problematic mathematically because local
coefficients do not intrinsically encode whether L2B will emit U or J. It is
still not the recommended baseline: the 242k-particle distribution and the
37k-panel-control-point distribution have different optimal leaf stopping,
refresh cadence, output storage, and routing. Sharing the world grid and
operator tables captures the low-risk reuse without forcing one topology.

## State Layers and Validity

Keep three layers explicit:

1. **World grid:** fixed origin/bounds, cell widths by level, Morton encoding,
   level numbering, and translation-operator tables.
2. **Role-specific sparse trees:** independent occupied cells, body
   permutations, leaf stopping, topology, and body/system index maps for
   particles, panel sources, and panel targets.
3. **Pass-specific numerical state:** source multipoles, target locals,
   interaction routes, nearfield workspaces, derivative layouts, and outputs.

Track at least two logical validity epochs:

- `geometry_epoch` invalidates keys, sorts, occupied topology, radii, and
  triggers occupancy and geometry-gate revalidation; and
- `strength_epoch` invalidates source multipoles while leaving geometry and
  routes reusable.

Track cross-tree route validity with the pair
`(source_occupancy_epoch, target_occupancy_epoch)`. Moving bodies within their
current cells does not invalidate a route cache provided their extent remains
inside the configured geometry gate; a change to either occupied node set or
the accepted stencil classification does. Strength-only changes never
invalidate routes.

Rigid motion can preserve a body-local solver topology and its leaf-indexed
cached blocks, but the combined world-aligned panel tree must refresh its
world-space keys/topology whenever panels cross grid cells. Panel multipoles
may be reused after a solve only when their recorded strength epoch matches the
accepted final strengths. A final defensive B2M→M2M refresh is preferable to
using a possibly stale Krylov/FGS operator application.

Target locals cannot be carried from panel targets to particle targets. The
source topology and current upward coefficients are the reusable portion; each
target hierarchy needs its own route, local coefficients, downward pass, and
output accumulation.

## Interaction Matrix

| interaction | source hierarchy | target hierarchy | production outputs |
|---|---|---|---|
| particles→particles | existing particle radix tree | same particle tree | U+J/SFS |
| particles→panels | existing particle tree/upward coefficients | combined panel-control-point tree | U unless an active consumer requires J |
| panel self solve | persistent per-body panel source tree | matching per-body solver target tree | boundary-equation quantity |
| cross-body solve, current block GS | ordered pairs of per-body panel trees | current body's solver target tree | boundary-equation quantity |
| cross-body solve, coupled prototype | combined all-panel source tree | combined panel-control-point tree | one global operator application |
| final panels→particles | combined all-panel source tree | reused particle target tree | U |
| final panels→panels | combined all-panel source tree | combined panel-control-point tree | only fields still required after the solve |

The first particle pass should reuse the particle upward pass for both
particles→particles and particles→panels where the source state is still
current. The final panel pass should reuse the combined panel topology and,
when epoch-valid, its final upward coefficients for panels→particles.

Do not automatically repeat panels→panels after the solve. Reuse the final
panel-target result only when it was evaluated at the accepted strengths and
contains the exact post-solve fields the downstream path needs; otherwise run
the missing panel-target output explicitly. In all cases, panels→particles
still requires its own target route and downward pass.

## Cross-Tree Interaction Lists

Separate source and target trees do not need identical topology or identical
Morton sorts. The production device path must extend the existing hierarchical
implicit-stencil lifecycle to two occupancy maps; it must not begin with a
generic pairwise dual-tree traversal.

For each active common level and fixed integer-offset class:

1. Enumerate occupied source nodes in canonical order.
2. Apply the existing phase/level stencil mask and compute the target lattice
   coordinate from the source coordinate plus the fixed offset.
3. Look up that coordinate in the target tree's device-resident occupancy map.
4. Compact successful lookups into class-major `(source_node, target_node)`
   route windows and apply the existing batched M2L operator for that class.
5. Generate leaf direct pairs from the role-specific fixed near-offset stencil
   by the same occupancy-lookup pattern, preserving panel conditioning and body
   tags.

The stencil classification, phase masks, and M2L operators are immutable grid
state reused by all cells and compatible source/target roles. Concrete route
endpoints are occupancy-dependent: generate them on device, retain bounded
window scratch, and cache the compacted per-level route concatenation while
`(source_occupancy_epoch, target_occupancy_epoch)` is unchanged. On an
occupancy-static step, route work is limited to the epoch check and cached
per-level apply; do not repeat flags, scans, compaction, route-count downloads,
or route uploads.

Select the fixed near/far stencil and any level schedule per interaction role
from accuracy and complete-leg timing. Include panel geometric extent and
regularization conservatively in that selection. Do not make a divergent
direct-versus-M2L cost decision for every node pair. Cells whose live extent
violates the selected stencil must fail the geometry gate or use an explicit
demotion/direct-exception path; they must not silently use an invalid M2L.

The v1 device path may require source and target trees to expose occupied nodes
at the same interaction levels even when their body permutations and leaf body
ranges differ. Arbitrary cross-level, independently stopped adaptive trees are
not a baseline requirement. Retain the host
`build_interaction_lists(target_branches, source_branches, ...)` traversal as
the correctness reference. A generic radius-aware dual-tree device traversal
is a later alternative only if it beats the implicit-stencil path on complete
leg time, route-build time, memory, and accuracy without losing class-major M2L
batching.

### Current block-GS solve

The present multibody solve is nested, not one frozen panels-on-panels pass.
Each body's FGS repeatedly evaluates its own panel farfield, and the outer
block Gauss–Seidel loop recomputes cross-body influence as panel strengths
change. Preserve its existing per-body solver trees and build/refresh one
implicit-stencil cross-tree route cache for each ordered
source-body/target-body pair. Refresh a cache only when either body's occupied
world-grid topology changes; changing panel strengths reuses its routes. This
keeps the current update ordering but loses high-level aggregation across
bodies.

### Coupled-solve prototype

Because solver redesign is allowed, benchmark the existing `KrylovCoupled`
formulation with the combined all-panel source and target trees. One global
matvec per Krylov iteration can aggregate all bodies and replace the ordered
cross-body passes. Use the existing per-body self solvers/cached blocks as the
reference and, if needed, as the basis of a block preconditioner.

Keep block/FGS as the production fallback. Adopt the coupled solve only if it
passes the locked science gates and reduces complete panel-solve plus
post-processing time enough to improve the full step by more than 10%. Do not
select it from isolated matvec time alone.

## Device Storage and Outputs

- Pack all active rigid-body panels into one tagged, capacity-sized device
  source array. Preserve system/body identity for conditioning, diagnostics,
  and result attribution.
- Keep the existing particle cache's 13-row output because particle
  self-influence requires U+J/SFS.
- Give production panels→particles a separate U-only local/output channel. Do
  not allocate or transfer particle J rows for this leg.
- Allocate panel-target J storage only when `requires_hessian` identifies an
  active consumer. The farfield local expansion may be shared by U/J L2B
  variants, but output slabs and accumulation channels remain target-specific.
- Do not allocate simultaneous particle and panel source multipole channels in
  v1. Every upward pass has one homogeneous source class.
- Allocate keys, permutations, nodes, coefficients, routes, and direct scratch
  to configured capacities, operate only on live prefixes, and fail loudly on
  capacity, bounds, or epoch violations.
- Instrument tree refresh/sort, B2M, M2M, route construction, M2L, direct,
  L2L, L2B, output accumulation, allocations, route counts, and total time per
  source/target role.

The extra combined panel hierarchy must be priced explicitly, but at the
production shape (about 36,752 panels versus 242k particles with J/SFS) its
storage should be modest relative to the particle cache. Measure rather than
assuming this conclusion.

Tune `p`, fixed near-offset radius and level schedule, common interaction
levels, source and target leaf body ranges, route-window capacity, and M2L
strategy independently by source/target role. Begin panel-source tuning at
`p=8`; do not force the particle tree's body permutation or leaf-body policy
onto either panel hierarchy merely because they share a world lattice.

## Per-Step Execution

1. **Particles on all:** refresh the particle tree once and run its upward pass
   once. Complete particle self U+J/SFS, then route the same current particle
   multipoles to the panel-control-point tree for U-only panel targets. A panel
   target that explicitly requests J uses a separate opt-in output path.
2. **Solve panel strengths:** use the persistent per-body solver trees under
   the current block/FGS formulation, including repeated self farfield and
   cross-body sub-interactions as strengths change. The coupled prototype
   instead performs one combined all-panel operator application per Krylov
   iteration. Neither path may advertise reusable final panel multipoles until
   its strength epoch matches the accepted solution.
3. **Panels on all required targets:** refresh the combined all-rigid-panel
   source topology if geometry changed and form final-strength multipoles once.
   Route them to the particle tree for U. Route them to panel targets only for
   fields not already available from an epoch-valid final solve application.

This ordering avoids rebuilding a particle hierarchy, builds only one
additional all-rigid-panel source hierarchy, and prevents a stale iterative
solve expansion from leaking into the final field evaluation.

## Implementation Order

1. Introduce the shared world-grid contract and role-specific tree metadata;
   leave the existing particle and per-body solver caches unchanged.
2. Generalize the device hierarchical implicit-stencil generator from one
   occupancy map to distinct source and target occupancy maps. Preserve
   class-major route order, bounded generation windows, and cached per-level
   concatenations keyed by the joint occupancy epoch.
3. Implement one combined homogeneous panel source tree and implicit cross
   routes to the existing particle target tree. Gate production U-only
   panels→particles first.
4. Add the combined panel-control-point target tree and particle→panel route,
   reusing the particle upward coefficients when current.
5. Add combined panel-source→panel-target routing as a replacement candidate
   for `panel_cross_targets`, while retaining the current ordered per-body
   routes.
6. Benchmark `KrylovCoupled` on the combined panel trees against the existing
   nested block/FGS solve. Adopt it only through the coupled-solve gate.
7. Add epoch-checked final panel multipole reuse and skip a post-solve
   panels→panels evaluation only when its accepted-strength result and output
   semantics are already available.

Configure particle and panel cross routes independently and keep each new
route default-off until its own gate passes. Reject invalid backend/parameter
values and log the effective grid, tree, derivative, and FMM settings once at
startup.

## Performance and Correctness Gates

- First run a near-peak checkpoint snapshot comparing CUDA dense, host FMM as
  an independent reference, and the combined device panel source tree routed
  to the reused particle target tree.
- Require steady-state `rotor_panels_to_particles_fmm < 0.6 s`, at least 2×
  leg speedup, and at least 1.0 s net total-step improvement. Include tree
  refresh, routes, transfers, synchronization, and GC.
- Verify cross-tree routing covers every source-target pair exactly once as
  either direct or farfield. Cover empty systems, multiple moving bodies,
  overlapping bounds, grid-boundary crossings, capacity growth, ground
  panels, and pre-existing output accumulation.
- Verify the cross-tree device route stream matches the host reference as a
  multiset and remains offset-class-major. Assert that strength-only updates
  preserve route-buffer identity and perform no route regeneration/upload;
  changing either occupied cell set advances the joint route epoch and rebuilds
  exactly once.
- Compare every leg independently with dense evaluation: particles→panels,
  panels→particles, panel self, and cross-body panel influence. Check global
  relative L2, maximum absolute error, scaled error percentiles/max, every
  panel kernel/tag, and finite outputs.
- Confirm derivative masks mechanically: particle self J/SFS remains present,
  panels→particles does not alter J, and panel J buffers/kernels are absent
  when no panel consumer requests them.
- Test epoch handling by changing strengths without geometry, changing
  geometry without body counts, reusing a current upward pass, and refusing a
  stale upward pass.
- Compare block/FGS and coupled Krylov convergence, final strengths, loads,
  iteration counts, determinism, and complete solve/post-processing time.
- Do not require strict monotonic error maxima with increasing `p`. Require
  the selected configuration to pass fixed error limits and a stricter
  configuration to materially reduce aggregate error.
- Add rigid covariance tests: translating and rotating a source/target
  configuration must rotate U and optional J correctly while preserving
  scalar error norms and near/far classification.
- Hold the existing science fingerprint and locked 36-step gates. Re-pinning
  is not an automatic performance fallback. Run the 1,080-step acceptance only
  after the snapshot and mature gates pass.

## Assumptions

- Production remains Float64. Particle self-influence emits U+J/SFS;
  body→particle emits U only under the current production configuration.
- Solver redesign is permitted, but block/FGS remains the fallback until a
  coupled alternative passes all performance and science gates.
- "Same implicit grid" means shared world coordinates and level geometry, not
  identical Morton sorts, leaf depths, or occupied-node tables.
- Production cross-tree routing uses the implicit fixed-offset stencil and
  joint occupancy-epoch caching; generic dual-tree traversal is not the v1
  device architecture.
- Source and panel-target records retain body identity even when placed in a
  combined tree.
- No pass in this item simultaneously forms multipoles from particles and
  panels.
- No changes are made to the running acceptance job or its tolerances.
- Dense remains the immediate fallback, with no silent runtime fallback after
  an explicitly selected FMM route fails.
